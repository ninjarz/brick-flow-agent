# 下一轮迭代计划：多项目工作台与可控 AI

规划日期：2026-09-08。建议作为下一功能版本的候选范围，版本号在发布时确定。本文件是计划，不代表已实施。

## 目标与依据

本轮已完成审查中的十项修复，验收记录为 408 个单元测试、15 个开发版浏览器流程和 2 个生产版浏览器流程通过。当前实现仍保存在工作区，尚未部署。下一轮应以这份实现建立基线，保留现有改动，避免从修复前版本重新开发。

建议以一个用户闭环作为目标：**创建项目 → 编辑场景 → 发起 AI 任务 → 查看与处理结果 → 切换项目 → 返回继续创作**。每一步都能明确知道当前项目、任务状态和保存状态。

依据：现有 workspaceSession 已建立事务边界，但持久化仍围绕单份草稿；AI 有取消、重试和导演调试能力，但任务生命周期分散；性能验证已有十秒基线，尚未覆盖长时间运行、多标签页写入和恢复故障。App.tsx 仍约 3840 行，拆分应伴随这两个产品闭环展开。

角色短目标、认知得分轨迹、相关角色快照筛选、角色火花预设均已实现，不作为新增任务重复安排。

## N0：固化基线与状态契约

将本轮已验证实现形成一个独立、可回退的版本基线，记录浏览器、操作系统、构建标识与测试数据。上线与后续开发分别安排，不把自动部署当作本计划的默认执行动作。

明确并测试三类行为：

- 项目内导入、替换与编辑可以撤销；模拟 tick 不写入编辑历史。
- 切换到另一个项目保存当前项目，每个项目拥有独立历史；不通过撤销按钮跨项目导航。
- 试演是临时会话，退出或重载恢复正式快照。关闭、切换项目或替换工作区后，旧 AI 任务不能提交结果。

输出简短状态转换说明、旧存档 fixture 与迁移测试。此次同时补齐真正经过 UI 的慢 Worker 回包及试演多次交互测试，覆盖上一轮主要通过领域单测验证的路径。

## N1：本地项目列表与安全切换

用户可以新建、命名、复制、打开和删除项目，看到当前项目名、最近保存时间及保存失败提示。现有素材库继续负责模型复用，项目列表负责完整工作区，避免将两种用途混为一体。

技术范围：

- 引入独立稳定的 projectId，导入文件中的 planId 不能直接决定覆盖哪个本地项目。
- IndexedDB 分离项目索引、工作区内容和恢复点；项目内容包含 plan、world、prompt 及 schemaVersion/revision。
- 从单草稿迁移为首个项目，写入并读回验证后才切换索引；保留旧草稿备份，迁移失败不得覆盖原始数据。
- 切换前完成当前保存或明确显示失败处理入口，不悄悄丢掉当前修改。不同项目隔离撤销历史、试演会话和 AI 任务。
- 打开列表仅加载索引，不批量解析所有模型或计算几何。

验收：迁移前后完整工作区语义一致；A/B 项目反复切换、重载后各自内容正确；导入两个同 planId 文件不会覆盖其他项目；保存失败、复制失败均不损坏源项目；50 个项目列表不会读取全部模型内容。浏览器流畅性使用固定设备和 fixture 测量后确定阈值。

## N2：恢复点与多标签页冲突处理

在导入替换、手动保存恢复点等关键操作前保留恢复点；自动保存仍合并频繁变化，不为每个模拟 tick 存储完整历史。

首版建议每项目保留最近 5 个恢复点，并配置总容量上限。清理只影响可淘汰恢复点，不删除唯一正式副本；容量不足时给出导出或清理入口。恢复操作先保留当前版本，再提交所选快照。

多标签页使用 IndexedDB 事务内的 revision 比较实现写入冲突检测。BroadcastChannel 可传递状态通知，但不承担数据正确性保证。检测到另一个标签页更新时，提供“重新加载”或“另存为新项目”，首版不实现自动合并场景。

验收：两个标签页同时编辑同一项目时不存在静默后写覆盖；后台标签页恢复后不能覆盖新版本；数据库配额不足、写入中断、迁移中断后至少保留一个可恢复正式版本；恢复点可完整恢复角色与剧情；已打开项目被另一标签页删除后不会被旧自动保存复活。

## N3：统一 AI 任务状态与诊断

整合建模生成、剧本节点、酒馆活动和导演请求的公共生命周期，复用已有 requestLifetime 与工作区失效机制。保留各领域自己的解析和执行规则。

用户界面区分：排队、请求中、接收中、校验/执行中、完成、取消、失败。失败说明区分网络、超时、限流、认证、格式和结构校验；提供与错误类型匹配的重试入口。导演已有的 token/上下文统计继续复用，不重复制作另一套统计。

技术范围：

- 统一 taskId、projectId、workspaceEpoch 和配置版本；限制同时执行的任务，切换项目时取消或失效旧任务。
- 默认诊断仅记录阶段耗时、结果类型、重试次数及服务实际返回的 usage；导出诊断不包含 API Key、提示词、图片或项目内容。
- 自动重试必须有上限；已经部分执行的剧情先确认事件去重或恢复检查点，再允许重试，防止重复加物品或重复修改世界。
- 为请求次数、输出 token 和连续失败提供可配置上限。供应商未返回 usage 时显示未知，不伪造费用；不内置未经验证的价格表。
- 抽出 useAiTasks 与领域执行适配器，让 App 负责组装。按职责减少耦合，不以文件行数作为验收指标。

验收：假服务覆盖排队取消、响应头延迟、body 停滞、SSE 断流、错误响应、无效 JSON、同项目乱序回包及跨项目回包；部分执行后的重试不重复产生副作用；新旧配置测试互不污染状态。固定一组建模/剧情 fixture，记录完成率和失败类型，不只检查 HTTP 200。

真实模型供应商兼容性测试单独列出待验证清单；实际调用需要可用测试凭据、选定供应商和预算，不能拿假服务通过冒充真实兼容。本次仅规划，不发起调用。

## N4：发布验收与长期运行

持续保留现有 verify:release。新增：

- 每次 PR：单元及浏览器关键流程、固定 seed 的世界不变量测试、迁移 fixture、双标签页冲突和假模型故障注入。
- 发布候选：30 分钟真实浏览器运行，组合暂停/继续、试演、导入和项目切换；记录每分钟堆、帧耗时、Worker 数量、事件与历史容量。
- 发布候选：Chromium 和 WebKit 的生产 smoke；验证存储、Worker、动态资源、下载与重载。低性能设备先测量后设明确支持范围。
- 检查 warm-up 后的内存趋势及可回收性，不能把一次 GC 前后堆下降当作不存在泄漏的证据。

退出条件：所有质量检查通过；故障序列下没有数据静默丢失；取消/切换后的迟到提交数为 0；恢复和迁移语义一致；没有未解释的持续资源增长。具体性能阈值在 N0 固定测试环境后锁定，避免共享 CI 机器波动造成误判。

## 里程碑与交付拆分

1. **M1 基线与项目骨架（约第 1 周）**：N0、项目 schema/迁移、基本列表和切换；形成可验证的数据流程。
2. **M2 恢复与任务整合（约第 2 周）**：完成恢复点和冲突保护，接入统一任务控制器。
3. **M3 验收候选（约第 3–4 周）**：任务交互完善、故障注入、长期运行和兼容性测试；修复测试发现的问题。

建议交付为六个可单独评审的变更：状态契约与回归；项目存储迁移；项目列表与切换；恢复点与冲突保护；AI 任务整合；运行验收与文档。此处仅定义工作拆分，不创建新任务或自动执行实现。

本轮范围止于本地多项目创作与任务可靠性。云同步、多人实时协作、新物理系统、新角色认知体系和更多素材包放入后续候选列表，避免扩大这一轮的数据模型与验收面。
